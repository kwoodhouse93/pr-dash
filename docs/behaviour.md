# How the dashboard behaves

What each part of pr-dash shows and does. Setting it up is in the [README](../README.md).

## Refreshing

The server uses `GITHUB_TOKEN` or `GH_TOKEN` when set, and otherwise `gh auth token`. A refresh pulls the open list you are looking at, then keeps that snapshot in `data/pr-dash.sqlite`. The server keeps that list moving about every minute, including while the tab is in the background, and pauses when few GraphQL points remain. Finished checks are kept when the pull request and its check rollup have not changed. Running checks are read again, and each refresh also rereads the checks that were fetched least recently so a quiet rerun still shows up. Thread replies load after the list, and again when a pull request changes. The row menu can refresh one pull request. Required checks are cached for a day. Settings has a full sync that reloads both lists and reads rulesets again.

Sort, filters, and which stacks are expanded are remembered in this browser. The address also carries the open page and its filters, so a filtered list can be bookmarked; a link that names a filter replaces the saved filters for that page.

## Keyboard

Press `/` to search, `j` and `k` to move through the rows, `.` to open the menu for the row, and `?` for the full list of keys. A popup closes with its cross, with Escape, or with a click outside it; one with a prompt typed into it stays until it is closed with its cross or Escape. In a popup the arrow keys move between its lines, and a line that shows a letter is pressed by that letter. The keyboard button in the header shows the same list.

## Settings

Settings chooses which repositories a refresh includes. Pick an owner, then the repositories under that owner. None are included until you select them, so a refresh does not ask GitHub about every repository you can access. Removing a repository deletes the pull requests, cached rules, agent sessions, and merge queue entries stored for it. That does not change the repository on GitHub.

Settings also picks a colour theme: Ember, Graphite, Ink and Moss are dark, and Paper is light. It is remembered in this browser, and the desktop app's window follows it on the next refresh. A theme changes the greys and the accent, which marks only where you are: the focus ring, the open tab, a pressed filter, the main button. The colours that say something stay the same in every theme: green for ready, red for broken, yellow for a warning, blue for waiting, purple for merged, and amber for yours to act on or work under way. Every colour is defined in `src/web/themes.css`, and a new theme is a block of inputs there plus a line in `src/shared/themes.ts`. Settings also has an Animations choice, kept the same way. System, which it starts on, follows your computer's reduce motion setting; On animates whatever the system says; Off stops everything that moves: the flights to the agents and the merge queue, confetti, sliding rows, folding sections and spinners. The desktop app's strip and sidebar follow it on the next refresh.

## Linear

`LINEAR_API_KEY` is optional. Without it, issue titles still come from the Linear link on the pull request. Project names, status, assignee, and linking a pull request to an issue need the key. Linking uses Linear’s GitHub attachment, so the workspace GitHub integration has to be connected. The link stays on the pull request after a refresh.

## Agents

Agents start from a row: resolve a merge conflict, investigate failing CI, fix a review thread, or run your own prompt. Each agent pushes to the pull request’s existing head branch. The dashboard remembers every session and refreshes active ones with the pull requests. Two providers can run them, and **Agents** in Settings picks which: one default, and any repository can use the other.

- **Cursor.** Cursor Cloud Agents, billed by Cursor. Set `CURSOR_API_KEY`. Create a user or service-account key in the Cursor dashboard. The key remains on this server.
- **T3 Code.** A thread in T3 Code on this machine, under the coding agent you are signed in to there. It needs the `t3` command (or `T3_BIN` set to its path), T3 Code running, and a T3 Code project for the repository. The dashboard finds that project by itself, from the GitHub repository its folder is a checkout of, and Settings shows which one it found. To work in another folder, or when it finds none, set a folder beside the repository in Settings. Each agent gets a new worktree made from the pull request’s branch on `origin`, so a pull request from a fork cannot be started this way. T3 Code works on this machine only, so a server deployed elsewhere should keep Cursor.

A T3 Code thread can open in a tab, where you can read it and reply. That needs this browser, or the desktop app, paired with T3 Code: **Pair** under Agents in Settings makes a one-time pairing link and uses it. The desktop app pairs out of sight and stays on Settings; a browser opens the link in a tab. The pairing lets this browser read threads and take part in them, nothing wider, and T3 Code keeps it for 30 days. It shows there under Sharing & access, where it can be revoked. If pairing by itself fails, *Enter a code* takes a pairing code from `t3 pair`. Until a browser is paired, a thread's link hands off to the T3 Code app. In the desktop app, that hand-off page carries a note offering to pair, with **Pair**, **View settings** and **Don’t ask again**. Pair does it there and then shows the thread in the same tab. Pairing is only offered when the dashboard runs on this machine.

Settings shows whether each provider is ready, and why not when it is not. If the provider for a repository cannot be used when you start an agent, the error says why and offers the other provider when that one is ready. It never switches by itself. A provider that stops answering while an agent runs does not fail the session: it keeps its last status, and its detail says since when that status may be out of date.

## Merged and closed pull requests

The dashboard keeps a record of every pull request that leaves a list because it merged or closed. A merge made by the merge queue is recorded as it lands. For any other pull request that has gone from a list, the next refresh asks GitHub what became of it, in one request for all of them, since leaving a list can also mean it closed or no longer asks for your review. One that is still open is not recorded, and one that is reopened is dropped from the record. The record starts from when this was added; earlier merges are not in it. Removing a repository deletes its part.

## What a row means

- **Age.** Time since the pull request was ready for review: when it last left draft, or when it was opened if it never was one. It is drawn as a ring that fills over two days. The ring is plain for three hours, turns yellow by the end of a day, and is full and red after two days. Hover or click the ring for the time itself. A pull request left waiting gathers a cobweb in the corner of the cell: a wisp after five days, more after two weeks, and the most after a month. A draft has a dotted ring that never fills, for the time since it was opened, with no colour or cobweb, and its row is dimmed. A stack shows its oldest pull request that is out of draft. The time comes with the next refresh; until then the row uses the time it was opened.
- **CI.** Passed is shown plainly, so the colours are the rows that need a look. Red means a required check failed, including a GitHub Actions workflow that failed before it created any jobs. Yellow means required checks are fine and an optional check failed. Blue means something is still running, or GitHub is still blocked on a required check that never reported. Hover a status for each check. A check from an older run of the same workflow does not count once a later run has replaced it, including a matrix job that was cancelled before it expanded and kept its bare name. Rerun failed, or rerun all, applies to GitHub Actions workflows on that row. Vercel and other external checks are listed and cannot be rerun from here.
- **Branch.** A red cross is a merge conflict. A white cross is a branch behind its base with no conflict. Nothing means it is up to date. Click a red cross to start an agent that resolves the conflict on the pull request’s existing branch; its status shows under Agents. When other pull requests are stacked above it, the agent is also asked to rebase each of them onto the resolved branch and push them, so the whole stack is left up to date. To resolve one branch and leave the rest alone, use *Work on this* with your own prompt. Click a white cross to rebase.
- **Review.** Three marks, in order: any approval, a human approval, and GitHub’s merge requirement (including code owners when that rule applies). Grey means no review is required, which is common on drafts and on stacked pull requests whose base is not the default branch. White is still waiting. Green means that mark is satisfied. Hover for the reviewers on each pull request: a green ring approved, a red ring asked for changes.
- **Feedback.** Each count sits beside an icon; hover one for its name and click it to open the feedback drawer filtered to it. The drawer has one filter per count plus All, which shows the conversation and every thread, so any click reaches everything. A thread you answer stays in view until you change the filter. On My PRs: threads awaiting you, comments, and unresolved threads. Awaiting you means the thread is unresolved and the latest human comment is not yours. On Review: unread threads you joined that have a newer reply, comments, resolved threads you joined that moved after you last spoke, and unresolved threads. A comment is a conversation comment or a review summary you have not answered. On Review the comment count is highlighted when one is a review summary or a conversation you already joined. Inline thread replies count as an answer. The total thread count shows only when nothing else does. GitHub has no way to resolve a conversation comment or review summary, so **Resolve** on the one you have not answered settles it on this dashboard only: it leaves the comment count and the row stops asking for you. A newer comment from someone else asks again, and **Unresolve** takes it back.
- **Merge.** A Merge button shows when the pull request targets the repository’s default branch and looks ready to squash: not a draft, not conflicting, not behind, and not blocked by required reviews or checks. One click puts it in the merge queue, which reads the pull request again, updates the branch if it has fallen behind, and squash-merges it. With nothing else in flight for that repository this happens straight away. The button folds into a small parcel, which waits until the queue has taken the merge and then swoops to the merge queue button in the top bar; if the queue refuses it, the parcel fades where it is. The row shows the queue’s status until the merge lands. When it lands, the row turns green for a moment and then goes, and the rows under it slide up. A stack merges from the bottom, one pull request at a time. Only the pull request next in line is rebased onto the trunk after each merge, so CI runs once for each pull request rather than again for every branch above each merge; until its turn, a pull request higher up can show extra commits on GitHub: on a collapsed stack the segment being merged pulses, and each one closes up as it lands. A notice names what landed, and the header counts your merges today with a tick for each. Beside it, in blue, it counts the pull requests you reviewed today: an approval, a request for changes or a review with comments all count, once for each pull request, and one still counts after it has merged. Only pull requests on the Review list are counted, so a review of one that never asked for you is not. A pull request the merge queue has merged stays off the list when a refresh still sees it as open. It comes back when GitHub reports that it is still open, or when a later queue attempt for it fails. Each repository runs its own line in the merge queue, so a merge waiting on checks in one repository does not hold up another, and the queue page shows one section per repository. A queued merge that fails is held aside, and the merges behind it carry on. On the row, hover or click the Failed badge for the reason; the queue page shows it in full. Retry, on the row or on the queue page, reads the pull request again and puts the entry back where it stood, so a fix you pushed since is what merges. Remove drops it. A retry of a stack that stopped part-way picks up where it left off: a branch still built on one that has merged is rebased onto the trunk before anything else. The queue merges only the commit it checked: if the branch gets a new head between the check and the merge, it reads the pull request again.
- **Merge without approval.** Off until you turn on "Allow merge without approval" in Settings. That only adds the option: Merge still waits for approval, and an unapproved pull request merges only when you choose the option for it. A pull request's menu then offers "Merge #N without approval" when its required approval is the only thing missing, including when GitHub blocks it without saying a review is required: it targets the default branch, is not a draft, has no conflict, no unresolved threads, no changes requested, and every required check has passed. It takes a second press to confirm, and the merge goes through the queue like any other, which still updates a branch that is behind and waits for its checks. GitHub has to let you bypass the review ruleset on the default branch, and the merge is refused if bypassing would also skip a rule the queue does not check itself, such as a required deployment. It is offered for one pull request at a time, never a stack, and only on your own list. A review that particular paths require from a team counts as an approval, so this skips that too.
- **Activity.** The Activity tab looks back at what you have merged and reviewed; the header's count for today opens it too. It shows this week against the same point of last week, the median time from ready for review to merged, and the median from ready to your first review. A chart gives each day of the last six weeks or three months, or each week of the last year, and under it are your records and a split by repository. Merges are counted from as far back as the dashboard has seen them. Reviews are logged as a refresh sees them, one entry for each review you submit on a pull request from the Review list, so their history starts when the log does; a pull request reviewed twice in a day counts once that day. Times from ready are only known for pull requests that left after this was added. When a merge or review takes today, or this week, past your best on record, a notice says so and confetti falls the width of the window; with reduced motion there is the notice alone. A best has to beat a day or week of at least two.
- **Agents.** Sessions started from this dashboard, in Cursor or T3 Code. Each row shows how many sessions it has, colored by the most active one: yellow while one waits for an answer, blue while one is creating or running, green when finished, red when failed, and grey when cancelled or expired. Click the count for a line on each session: what it is for, its status, and when it started. Click a line to open a sidebar with a section for each session, holding its prompt, final reply, pushed branch, links to the session in Cursor or T3 Code, and a button that copies the reply. Statuses update when the dashboard refreshes. The robot button in the top bar opens the **Agents** page, which lists every session on both lists: the ones waiting for an answer first, then the ones running, failed and finished. The button counts the agents at work and carries a yellow mark while one waits for you. An agent is listed from the moment you start it, as creating, while its provider sets it up. Its task folds up where you started it and swoops to that button, with a rush on the way and a note as it lands when sounds are on. With reduced motion it does not fly.
- **Row menu.** *Link Linear issue* attaches this pull request to an issue. Merging the pull request does not close that issue. *Work on this*, under *Cursor* or *T3 Code*, starts an agent with your prompt, plus the pull request’s link, branches, and linked issues. *Investigate CI failure* appears when a check failed, and is also in the CI popover. That agent reads the failing logs, pushes a fix when the cause is clear, and otherwise reports what it found. A conflict or CI agent runs once at a time on a pull request. Prompts can run side by side.

A row whose checks, review or feedback changed while the dashboard was open is tinted for a few seconds, so a change is seen without reading every row. Opening a stack draws its rail down and brings its rows in one after another. When the system asks for reduced motion, none of this moves: panels open and close at once, a merged row goes straight away, nothing pulses, and the icon's bars hold still.

Required check names come from each repository’s rulesets, so a check that is required to land on the default branch still counts as required on a stacked pull request.

## Stacks and headings

A collapsed stack shows one segment for each pull request, the bottom of the stack first. Green can merge now, amber needs you, red has a conflict or failing CI, grey is waiting on someone else, and an outline is a draft. On Review, green means you approved it. Hover a segment for the pull request number.

A stack with branches is one stack, and each pull request is listed once. Collapsed, the row is named after the top of the part every branch shares, the strip splits into a line for each branch, and the row says how many branches there are. Expanded, the rail gives each branch its own lane and curves in where a branch joins the pull request it is based on. Merging a pull request merges it and the ones below it, and restacks every other branch in the stack. Rebasing one restacks every branch above it. A branch that is neither above nor below what a section shows is left out of that section.

Project, issue and initiative headings count the same states for the rows under them, so a collapsed heading still says whether it needs you.

## The icon

The browser tab's icon and the desktop app's Dock icon say whether to look. The top bar is red when something is broken: a required check failed on one of your pull requests that is not a draft, or a merge is held in the queue. Otherwise it is amber, with a count, when pull requests wait on you: yours with replies to answer or ready to merge, and ones to review. With nothing waiting, all three bars are green. While the merge queue works, the bars ripple.

## Repositories

Each repository has an icon and a colour. It starts with a pair chosen from its name, and you can change it beside the repository in Settings. The Repo column shows the icon, and is hidden when every pull request in the list is in one repository. The merge queue shows it beside each repository name.

## Initiatives

Initiatives are tags stored in this app, not on GitHub. Create, rename, and delete them in Settings. Use them for cleanup, refactors, and other work that has no Linear project. A pull request can have more than one. A pull request with a Linear project stays under that project; the initiative chip still shows on the row. A stack that also contains other work shows `…` rows above or below the slice in that section.

## Desktop app

**Sidebar.** The button at the left of the tab strip, or ⌃⌘S, swaps the strip's tabs for a sidebar, and the strip then names the page you are on. The sidebar lists open tabs only. A tab on a pull request the dashboard knows shows that pull request's title, check status and the number of comments waiting on you, whether the tab is on GitHub or Graphite. The picker beside Tabs groups them as the dashboard does, by project, issue, initiative or stack, or not at all. Groups and the pull requests in them come in the dashboard's order, so a stack reads top to bottom. A line through the status dots joins the open pull requests of a stack: dotted where pull requests between two rows are not open, a short dotted end where the stack goes on above or below, and a second lane for a branch, which curves in at the pull request it is based on. Hover a row to see what it is based on. A page opened from a pull request sits under it. Linear pages have a section of their own, grouped by project, which is known for issues and projects linked to a pull request on the dashboard. Linear Tabs by Project in the picker turns that grouping off. A tab on a pull request that has merged or closed keeps its place, after the open ones in its group, with a purple dot for merged and a grey one for closed in place of its checks. Other pages that belong to no pull request go under Other. A dashboard link to a pull request that already has a tab goes to that tab. When a tab leaves its pull request the row takes the new page's name at once, and moves to its new place when you switch to another tab. Drag the sidebar's right edge to resize it, or double-click the edge to reset it. Merge queue and Settings at the bottom switch the dashboard to those pages; Pull requests at the top goes back to the list, at the place you left it. ⌘+ and ⌘- zoom the page, or the strip and sidebar when you last clicked there. Closing a tab returns to the tab you were on before it.

**Agents.** The sidebar lists every agent started from the dashboard that is running, or that finished or failed since you last looked at it. Click one to open it, which marks it read; it keeps its row until you switch to another tab. The × sets it aside without opening it. Read and set-aside agents are under Earlier. With the sidebar hidden, a count in the strip opens the same list. An agent's tab opens behind the dashboard, and its task flies from where you started it to its row in the sidebar, or to the count in the strip. **Agents** at the foot of the sidebar, and *View all agents* in the strip's list, open the dashboard's Agents page. An agent whose pull request has merged or closed stays in the list. What you have read is kept in `agents.json` in the app's data folder.
